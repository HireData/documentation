_If you're building an automation or an integration on top of Carerix data and need to know what a field is actually called — the record ID, the email address, the candidate's name — this page tells you where those names come from and how to read them for your own connection._

## What HireData receives from Carerix

Carerix sends HireData an **event** whenever something happens in your system: a candidate created, a match updated, and so on. HireData normalises that into an event record with a fixed shape, which is what your automations then work with.

This is worth knowing up front, because it answers the most common version of this question:

<Note>
  **Can I see the raw Carerix request body?** Not as raw JSON, no. What you get instead is the normalised event, split across two tabs that between them show everything Carerix sent: **Event Data** (the fields HireData mapped and your automations can use) and **External Records** (additional fields from Carerix, including ones no automation uses). See [Events](/settings/logs/events).

  If you specifically need to see a literal request body, use a [Custom App trigger](/apps/custom-apps/set-up-a-trigger) — it stores every request it receives and shows you the parsed fields, keys and types.
</Note>

## Where the field names come from

The exact set of Carerix fields available to you is **specific to your connection**, because you choose which ones sync. There are two reliable places to read them:

<Steps>
  <Step title="The connection's field list — the authoritative source">
    Go to **Settings → Apps → Carerix**, click **Edit** on your connection, and open an object (Candidate, Match, Appointment, and so on). You'll see every field on that object and whether it's toggled on. Only fields toggled on are available to automations. See [Enable Carerix fields and relationships in automations](/apps/carerix/how-to-enable-carerix-fields-and-relationships-in-your-automations).
  </Step>
  <Step title="A real event — the fastest source">
    Go to **Settings → Events**, filter by Carerix, and open a recent event. **Event Data** shows the mapped fields with their values; **External Records** shows the additional fields Carerix sent that aren't used by an automation. This is the quickest way to answer "what did Carerix actually send for this candidate?"
  </Step>
</Steps>

## The identifier

Each Carerix record carries an ID, exposed in HireData as the object's **ID** field — `Candidate: ID`, `Match: ID`, and so on. This is what automations match on: the **Update fields** task, for example, matches the `Candidate: ID` from the conversation against the `Candidate: ID` in the database to make sure the right record is updated.

Use the object's ID field rather than an email address or a name when you need a stable identifier — emails and names change, IDs don't.

## Email addresses

Carerix records can hold several email addresses at once, so HireData exposes both the individual fields and a **combined field** that picks the first one with a value.

Use `anyEmailAddress` when you just need a working email address. The individual fields behind it, in the order HireData checks them, are documented in full in [Combined Fields Explained](/apps/carerix/combined-fields-explained) — the first two checked are `businessOrPrivateEmailAddress` and `privateOrBusinessEmailAddress`, and the plain `businessEmailAddress` and `privateEmailAddress` fields sit further down the order.

The same pattern applies to phone numbers via `anyPhoneNumber`. `CarerixCandidate`, `CarerixUser` and `CarerixContact` all use the identical set of combined fields.

## Names

Name fields are exposed per object as ordinary fields — first name, last name and the derived full name — and are toggled on per connection like any other field. Check your connection's field list (step 1 above) for the exact set enabled on your Candidate object.

<Tip>
  If you're picking fields for an automation, use the variable picker rather than typing keys. It shows the readable label ("Contact: First Name") alongside the underlying key, which removes the guesswork entirely.
</Tip>

## Which event types exist

Carerix triggers are defined per object and per action. The documented and commonly used form is **created or updated** on an object — for example, `Match: Created or Updated`, which is what the WhatsApp Job Alert template uses. You choose the trigger when you build the automation; see [Create a Carerix automation in HireData](/apps/carerix/create-a-carerix-automation-in-hiredata).

<Warning>
  Whether a **deleted** event type is available for Carerix objects is currently being confirmed. Don't design an automation around delete events until it's documented here.
</Warning>

To see which trigger fired for a specific event, open the event and check the **Processes** tab — it lists the automations that event triggered and the runs it created. See [Events](/settings/logs/events).

## Still need help?

If you need a field that isn't appearing, first check it's toggled on in your connection, then run a [manual sync](/apps/carerix/manually-sync-carerix-with-hiredata) so recent changes in Carerix are reflected in HireData. If it still isn't there, contact us at [support@hiredata.com](mailto:support@hiredata.com) with:

- The name of the Carerix object and the field you're looking for;
- A link or the ID of an event that should have contained it.
